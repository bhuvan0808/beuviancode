# Database Documentation

**Status: design. Implemented in Phase 2.**

This document records the schema and the reasoning behind it, so the Phase 2
migrations are a transcription rather than a fresh set of decisions.

Target: **Supabase PostgreSQL**. Nothing in the schema is Supabase-specific — it is
ordinary PostgreSQL, which is what keeps the deployment replaceable and lets the
local Postgres container behave identically.

---

## Conventions applied throughout

| Convention | Reason |
| --- | --- |
| `TEXT` primary keys holding prefixed ULIDs (`dev_01J9Z…`) | Time-sortable, so inserts land at the right edge of the B-tree instead of scattering random pages. Prefixes make a stray ID self-describing in a log line. See [ADR-0005](adr/0005-ulid-identifiers.md) |
| `created_at`, `updated_at` — `TIMESTAMPTZ NOT NULL DEFAULT now()` | `TIMESTAMPTZ`, never `TIMESTAMP`: users are in many time zones and a naive column silently loses the offset |
| `deleted_at TIMESTAMPTZ` for soft deletes | Only where recovery matters (see below) |
| `organization_id TEXT` nullable, unused in the MVP | PROJECT.md defers teams. Adding the column now means enabling them later is a constraint change, not a backfill of every row |
| Every foreign key has an explicit `ON DELETE` | The default `NO ACTION` produces confusing failures at delete time rather than a stated policy |
| Every foreign key is indexed | PostgreSQL does **not** create these automatically, and a missing one turns a cascade delete into a sequential scan per row |

### Where soft deletes apply, and where they do not

Soft-deleting everything is a common mistake: it forces `WHERE deleted_at IS NULL`
into every query, and one omission silently resurrects deleted data.

| Soft delete | Hard delete |
| --- | --- |
| `users`, `devices`, `repositories` — user-visible things whose accidental deletion is worth undoing, and which are referenced by historical sessions | `session_logs`, `prompt_queue`, `agent_status`, `refresh_tokens` — high-volume or ephemeral, where retention is a liability rather than a safety net |

A revoked `refresh_token` is deleted outright. Keeping a revoked credential row
"just in case" is the opposite of what revocation means.

## Tables

### `users`

| Column | Type | Notes |
| --- | --- | --- |
| `id` | `TEXT PK` | `usr_…` |
| `github_id` | `BIGINT UNIQUE NOT NULL` | GitHub's numeric ID, **not** the login |
| `github_login` | `TEXT NOT NULL` | Denormalised for display |
| `email` | `TEXT` | Nullable — GitHub users may hide it |
| `name`, `avatar_url` | `TEXT` | |
| `organization_id` | `TEXT` | Future |
| `last_login_at` | `TIMESTAMPTZ` | |
| `created_at`, `updated_at`, `deleted_at` | | |

The unique key is `github_id`, not `github_login`, because **logins are renameable**.
Keying on the login means a user who renames their GitHub account becomes a
different person and loses their devices and history.

### `oauth_accounts`

Separate from `users` so a second provider is a new row rather than a schema change.

| Column | Type | Notes |
| --- | --- | --- |
| `id` | `TEXT PK` | |
| `user_id` | `TEXT NOT NULL → users(id) ON DELETE CASCADE` | |
| `provider` | `TEXT NOT NULL` | `github` |
| `provider_user_id` | `TEXT NOT NULL` | |
| `access_token_encrypted` | `TEXT` | Encrypted at rest, never plaintext |
| `scopes` | `TEXT[]` | |

`UNIQUE (provider, provider_user_id)`.

Beuvian stores a GitHub token only for reading repository metadata. It is **never** a
model-provider credential — Beuvian holds none.

### `devices`

| Column | Type | Notes |
| --- | --- | --- |
| `id` | `TEXT PK` | `dev_…`, generated by the agent |
| `user_id` | `TEXT NOT NULL → users(id) ON DELETE CASCADE` | |
| `name` | `TEXT NOT NULL` | Hostname by default |
| `platform` | `TEXT NOT NULL` | `windows/amd64` |
| `agent_version` | `TEXT` | For diagnosing version-specific reports |
| `capabilities` | `TEXT[]` | Adapters **installed**, from the AUTH handshake |
| `token_hash` | `TEXT NOT NULL` | See below |
| `token_expires_at` | `TIMESTAMPTZ NOT NULL` | |
| `last_seen_at` | `TIMESTAMPTZ` | |
| `revoked_at` | `TIMESTAMPTZ` | Distinct from `deleted_at` |
| `created_at`, `updated_at`, `deleted_at` | | |

**Only the token hash is stored.** A database dump must not yield working device
credentials. `revoked_at` is separate from `deleted_at` because revoking a
compromised device's access is not the same act as removing the device from the
user's list, and conflating them makes "revoke but keep the history" impossible.

`capabilities` records what is installed rather than what the binary supports, so the
backend never dispatches a prompt to a device that cannot service it.

### `repositories`

| Column | Type | Notes |
| --- | --- | --- |
| `id` | `TEXT PK` | `rep_…` |
| `user_id` | `TEXT NOT NULL → users(id) ON DELETE CASCADE` | |
| `full_name` | `TEXT NOT NULL` | `owner/name` |
| `local_path` | `TEXT` | Path on a specific device |
| `device_id` | `TEXT → devices(id) ON DELETE SET NULL` | |

`ON DELETE SET NULL` on `device_id`: removing a laptop should not delete the record
of repositories worked on there. `UNIQUE (user_id, full_name, device_id)`.

### `sessions`

| Column | Type | Notes |
| --- | --- | --- |
| `id` | `TEXT PK` | `ses_…` |
| `user_id` | `TEXT NOT NULL → users(id) ON DELETE CASCADE` | |
| `device_id` | `TEXT NOT NULL → devices(id) ON DELETE CASCADE` | |
| `repository_id` | `TEXT → repositories(id) ON DELETE SET NULL` | |
| `adapter` | `TEXT NOT NULL` | `claude` |
| `state` | `TEXT NOT NULL` | The `AgentState` enum |
| `current_task` | `TEXT` | Best-effort |
| `working_directory` | `TEXT NOT NULL` | |
| `pid`, `exit_code` | `INTEGER` | `exit_code` nullable — NULL means "has not exited", which `-1` cannot distinguish from a real code |
| `started_at` | `TIMESTAMPTZ NOT NULL` | |
| `ended_at` | `TIMESTAMPTZ` | NULL while running |
| `created_at`, `updated_at` | | |

`state` is `TEXT` with a `CHECK` constraint rather than a PostgreSQL `ENUM`. Adding a
value to an `ENUM` requires `ALTER TYPE`, which historically could not run in a
transaction and complicates rollback; a `CHECK` constraint is edited like any other
constraint. The values are validated in Go regardless.

Partial index for the hot query — "is anything running on this device?":

```sql
CREATE INDEX idx_sessions_active ON sessions (device_id, started_at DESC)
    WHERE ended_at IS NULL;
```

A partial index stays small no matter how much history accumulates, because the
overwhelming majority of rows are finished sessions.

### `session_logs`

The highest-volume table by a wide margin.

| Column | Type | Notes |
| --- | --- | --- |
| `id` | `BIGSERIAL PK` | Not a ULID — see below |
| `session_id` | `TEXT NOT NULL → sessions(id) ON DELETE CASCADE` | |
| `seq` | `BIGINT NOT NULL` | Per-session ordering |
| `stream` | `TEXT NOT NULL` | `stdout` / `stderr` / `system` |
| `content` | `TEXT NOT NULL` | One or more lines |
| `truncated` | `BOOLEAN NOT NULL DEFAULT false` | |
| `at` | `TIMESTAMPTZ NOT NULL` | Producer's timestamp |
| `created_at` | | |

`BIGSERIAL` here rather than a ULID: this table takes the highest insert rate, and 8
bytes per row versus 26 is a material difference across millions of rows in both
table and index size. Log rows are never referenced by external clients, so the
self-describing-ID argument does not apply.

`UNIQUE (session_id, seq)` makes ingestion **idempotent** — a redelivered batch after
a reconnect conflicts instead of duplicating the transcript.

Retention matters and should be decided before launch, not after: append-only log
data grows without bound. `PARTITION BY RANGE (created_at)` monthly is the intended
approach, since dropping an old partition is instant while `DELETE` on millions of
rows is not.

### `prompt_queue`

**The durable system of record for prompts.** Redis is only an accelerator — see
[ARCHITECTURE.md §7](ARCHITECTURE.md#7-data-what-goes-where).

| Column | Type | Notes |
| --- | --- | --- |
| `id` | `TEXT PK` | `prm_…` |
| `user_id` | `TEXT NOT NULL → users(id) ON DELETE CASCADE` | |
| `device_id` | `TEXT NOT NULL → devices(id) ON DELETE CASCADE` | |
| `session_id` | `TEXT → sessions(id) ON DELETE SET NULL` | |
| `text` | `TEXT NOT NULL` | |
| `status` | `TEXT NOT NULL` | `pending` / `dispatched` / `delivered` / `failed` / `cancelled` |
| `attempts` | `INTEGER NOT NULL DEFAULT 0` | |
| `enqueued_at` | `TIMESTAMPTZ NOT NULL` | |
| `dispatched_at`, `delivered_at` | `TIMESTAMPTZ` | |
| `error` | `TEXT` | |
| `correlation_id` | `TEXT` | Ties the row to its trace across processes |

The prompt is committed here **before** the API acknowledges the user. If Redis then
loses the dispatch message, the prompt is still delivered from this table on the next
reconnect. That ordering is the reason a user's instruction cannot be lost by a Redis
restart, and it is why `redis.required` defaults to `false`.

```sql
CREATE INDEX idx_prompt_queue_pending ON prompt_queue (device_id, enqueued_at)
    WHERE status = 'pending';
```

### `agent_status`

Latest resource snapshot per device — one row per device, updated in place.

| Column | Type | Notes |
| --- | --- | --- |
| `device_id` | `TEXT PK → devices(id) ON DELETE CASCADE` | |
| `state` | `TEXT NOT NULL` | |
| `cpu_percent` | `REAL` | |
| `memory_bytes` | `BIGINT` | |
| `queued_prompts` | `INTEGER` | |
| `reported_at` | `TIMESTAMPTZ NOT NULL` | |

Deliberately **not** a time series. Updating one row per device per 10s heartbeat is
cheap; appending forever would make this the largest table in the database in
exchange for history nobody asked for. If historical graphs are wanted later, that is
a separate purpose-built table.

### `refresh_tokens`

| Column | Type | Notes |
| --- | --- | --- |
| `id` | `TEXT PK` | |
| `user_id` | `TEXT NOT NULL → users(id) ON DELETE CASCADE` | |
| `token_hash` | `TEXT NOT NULL UNIQUE` | SHA-256; the plaintext exists only in the cookie |
| `family_id` | `TEXT NOT NULL` | Rotation lineage |
| `expires_at` | `TIMESTAMPTZ NOT NULL` | |
| `used_at` | `TIMESTAMPTZ` | Set on rotation |
| `user_agent`, `ip_address` | `TEXT` | For a "your sessions" view |

**Rotation with reuse detection.** Each refresh issues a new token in the same
`family_id` and marks the old one `used_at`. If an already-used token is presented,
the entire family is revoked — that pattern means a token was stolen and both the
attacker and the legitimate user are now using it, so ending every session in the
family is the correct response.

Only hashes are stored, so a database dump cannot be replayed as a login.

### `audit_log`

| Column | Type | Notes |
| --- | --- | --- |
| `id` | `BIGSERIAL PK` | |
| `user_id` | `TEXT → users(id) ON DELETE SET NULL` | |
| `action` | `TEXT NOT NULL` | `device.revoked`, `prompt.sent` |
| `target_type`, `target_id` | `TEXT` | |
| `metadata` | `JSONB` | |
| `ip_address`, `user_agent` | | |
| `correlation_id` | `TEXT` | |

`ON DELETE SET NULL`, not `CASCADE`: deleting a user must not erase the audit trail
of what that user did. That is the one place where preserving the row outranks the
cascade, and getting it wrong makes the audit log useless precisely when it matters.

## Connection pooling on Supabase

Use the **pooler endpoint (port 6543)** in production, not the direct connection
(5432). Supabase caps direct connections, and several backend instances each opening
`max_open_conns` will exhaust that cap — at which point every instance starts failing
at once, which reads as a total outage rather than a configuration error.

`database.max_open_conns` (default 25) must be sized as
`instances × max_open_conns < Supabase's limit`.

## Migrations

Plain versioned SQL in [`backend/migrations/`](../backend/migrations/). Migrations do
**not** run at application startup — during a rolling deploy several instances would
race, and at worst two concurrent DDL statements deadlock with the schema
half-applied. They run as an explicit single-instance CI step.

See [`backend/migrations/README.md`](../backend/migrations/README.md) for the
expand-then-contract rules that keep a rolling deploy working while both application
versions are live.
